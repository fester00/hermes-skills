# Разделение смешанных списков в `template_data`: пример Пента-811/870

## Контекст

В категории `production-waterproof` (гидрофобизаторы и смывки высолов) v1-описание товара содержало несколько разных `<ul>`-списков под общими подзаголовками:

- «Обрабатываемые поверхности»
- «Ключевые свойства» / «Ключевые преимущества»
- «Способ применения»
- «Рекомендация» / «Внимание»

При миграции все пункты попали в одно поле `bullets`, а обрывки подзаголовков остались в `body`. В результате секция «Описание» на странице товара рендерила:

1. вводный текст + ТУ
2. один длинный список из 11–14 пунктов (поверхности + свойства вперемешку)
3. пустые/дублирующие подзаголовки после списка

Это создавало визуальный отступ и путаницу: пользователь видел «Экологически безопасен», а затем пустое место от обрезанного заголовка.

## Корректная структура

`UniversalTemplate.tsx` рендерит секцию «Описание» через отдельные поля:

| Поле | Что рендерит | Пример для Пента-811 |
|---|---|---|
| `intro` | Вводный абзац | Краткое описание гидрофобизатора |
| `body` | Дополнительный текст без подзаголовков | Сертификация, технологическое сопровождение |
| `surfaces` | «Применимые поверхности:» + список | Кирпич, камень, бетон, шифер |
| `properties` | «Особенности:» + список | Эффект лотоса, паропроницаемость, морозостойкость |
| `recommendations` | «Рекомендации» + список в секции «Применение» | Разведение, нанесение, расход |
| `method` | «Способ нанесения» в «Доп. информации» | - |
| `important_note` | «Важно:» в секции «Применение» | Про краскопульт, стёкла, температуру |

## Алгоритм разделения

1. **Выделить v1-блоки** из `src/data/products.tsx` по HTML-тегам `<p><strong>...:</strong></p>` + следующий `<ul>`.
2. **Поверхности → `surfaces`**: любые пункты с перечислением материалов (кирпич, камень, бетон, шифер, плитка).
3. **Свойства/преимущества → `properties`**: эффекты, защитные характеристики, безопасность, экономичность.
4. **Инструкции → `recommendations`/`method`**: пункты с глаголами (нанесите, разведите, смыть, выдержать, распылять).
5. **Важные замечания → `important_note`**: предупреждения, ограничения температуры, тара.
6. **Удалить `bullets`**, если он содержит смесь вышеперечисленного — иначе `DescriptionSection` отрисует его ещё раз поверх `surfaces`/`properties`.
7. **Очистить `body`/`intro`** от обрывков подзаголовков (`Обрабатываемые поверхности:`, `ТУ:`, `Способ применения:`). Оставить только плоский текст.

## Важное уточнение: «Особенности» в шапке товара

Секция «Особенности:» в верхней карточке товара (рядом с ценой и фасовкой) берётся из **отдельной колонки** `products.features`, а не из `template_data.properties`.

```tsx
// src/components/UI/Cards/ProductCard.tsx
<ul className="list-group list-group-flush mb-4">
  {product.features.map((feature, i) => (
    <li key={i} className="list-group-item px-0 bg-transparent border-bottom-0 py-1">
      ✅ {feature}
    </li>
  ))}
</ul>
```

Это означает:
- Изменения в `template_data.properties` влияют только на секцию «Описание».
- Если «Особенности» в шапке пустые или устаревшие — править нужно колонку `features` в `products`, а не `template_data`.
- Дублирование между `features` и `properties` допустимо, но желательно держать `features` короткими (3–4 пункта) для шапки, а `properties` полными для SEO.

## Урок по merge бинарного `.db`

SQLite-база `pentajunior.db` хранится в git как бинарный файл. Если пользователь запушил правки удалённо, а затем вы сделали свои правки локально, `git pull` выдаст конфликт:

```
warning: Cannot merge binary files: pentajunior.db (HEAD vs. d32c491...)
CONFLICT (content): Merge conflict in pentajunior.db
```

Разрешение:

```bash
# если ваши локальные изменения должны сохраниться
git checkout --ours pentajunior.db
git add pentajunior.db
git commit -m "merge: сохранить локальные изменения БД"

# если удалённые изменения важнее
# git checkout --theirs pentajunior.db
```

После merge важно сравнить обе версии БД через Python/SQLite, чтобы не потерять правки пользователя. Если обе версии содержат ценные изменения, извлеките их скриптом и объедините вручную, а затем перезапишьте `pentajunior.db`.

## Проверка после правок

1. `npx tsc --noEmit`
2. `rm -rf .next && npm run build`
3. `pkill -9 -f 'next-server'` (или `pgrep -a next` для проверки зомби)
4. `npx next start --port 3001`
5. `curl -s http://localhost:3001/production/production-waterproof/penta-870 | grep -o 'Применимые поверхности\|Особенности' | sort | uniq -c`
6. Визуальная проверка: секция «Описание» должна содержать два чётких списка без пустых отступов.
