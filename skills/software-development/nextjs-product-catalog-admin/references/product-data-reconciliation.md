# Согласование product-данных: template_data vs spec-таблицы

## Когда применять

После первичного переноса товаров из legacy `products.tsx` в SQLite новой версии проекта (`pentajunior-v2`). На этом этапе часто оказывается, что:

- технические характеристики продукта дублируются и в `template_data`, и в `spec_tables`;
- у товаров без семейной spec-таблицы в описании есть чёткая секция «Характеристики», которую логично вынести в персональную таблицу;
- админ-форма редактирования товара стала перегружена повторяющимися полями.

## Подход: точечная коррекция, а не полный пересчёт

Предпочтительный подход пользователя — не пересобирать `template_data` для всех товаров заново, а аккуратно удалить дубли и создать недостающие таблицы. Скрипт для этого лежит в `scripts/reconcile-product-spec-tables.py` скилла; копируется в проект и адаптируется под конкретный набор товаров.

## Алгоритм

### 1. Извлечь legacy-данные

Используем `tsx`, чтобы импортировать TypeScript/TSX-массивы из действующего проекта и сохранить в JSON:

```ts
// /tmp/dump_products.ts
import { products } from '/home/natan/workspace/pentajunior/src/data/products.tsx';
import { writeFileSync } from 'fs';
writeFileSync('/tmp/legacy_products.json', JSON.stringify(products, null, 2));
```

```bash
npx tsx /tmp/dump_products.ts
```

Аналогично для `SpecTables.tsx`.

### 2. Преобразовать React-деревья в markdown/текст

JSX `description` и `application` хранятся как JSON-сериализованные React-элементы. Нужен конвертер `react_to_markdown`, который обходит узлы и выдаёт:

- параграфы с `**жирным**`;
- списки `- пункт`;
- заголовки `### Заголовок`.

Это позволяет распарсить секции по `### `.

### 3. Сопоставить ключи template_data со строками spec-таблицы

Примерная карта:

| template_data key | строка в spec-таблице |
|---|---|
| `ratio` | соотношение, весовое |
| `viscosity` | вязкость |
| `hardness` | твердость |
| `elongation` | удлинение, эластичность |
| `shrinkage` | усадка |
| `pot_life` | время жизни |
| `cure_time` | время отверждения |
| `color` | цвет |
| `certificates` | fda, bfr, сертификат |

### 4. Нормализация для сравнения значений

- Убрать пробелы, неразрывные пробелы, единицы (`мПа·с`, `Шор А`).
- Для чисел оставить только цифры и разделители.
- Для `ratio` привести к простейшему виду (`100:100` → `1:1`).
- Для кириллицы/латиницы в марках (`6v` vs `6В`, `TRANS` vs `trans`) — нормализовать транслитерацию.

### 5. Удалить дубли

Если значение из `template_data` совпадает со значением в колонке текущего товара в его spec-таблице — удалить ключ из `template_data`.

### 6. Создать персональные spec-таблицы

Для товаров без `spec_table_id`, но с секцией «Характеристики» / «Технические характеристики»:

- id таблицы: `{product_id}-specs`;
- колонки: `['Характеристика', 'Значение']`;
- строки: распарсенные пункты вида `Название: значение`.

После создания привязать `product.spec_table_id` к новой таблице.

### 7. Всегда делать бэкап БД и писать лог

```python
shutil.copy(DB_PATH, BACKUP_PATH)
```

Лог должен содержать каждое удалённое поле и каждую созданную таблицу — для ручной проверки.

## Подводные камни

- **Пересечение поверхностей и характеристик.** Поле `surfaces` в герметиках описывает области применения, а не технические параметры. Не удалять его, даже если у товара есть spec-таблица.
- **Смешанные данные в полях.** Некоторые legacy-поля могут содержать и характеристики, и инструкции по применению. В таких случаях лучше оставить поле как есть, чем потерять инструкции.
- **Сертификаты.** Значение в `template_data` (`FDA/BfR`) и в таблице (`да`) почти никогда не совпадают текстом. Для `certificates` достаточно совпадения по названию строки таблицы.
- **Двойное экранирование при записи скриптов.** Если генерировать Python-скрипт через `execute_code`, а затем править его `patch` — обратить внимание на обратные слэши и f-строки. Инструменты могут переэкранировать `\n` → `\\n`. Лучше писать скрипт целиком через `write_file`.
- **Сопоставление колонок в семейных spec-таблицах.** Колонки часто названы по короткому марочному индексу (`9110`, `9120`, `6В`, `TRANS`), а `product.id` содержит полное имя (`unisil-9120`, `unicast-6v`, `unicast-trans`). Прямой подстроковый поиск `pid` в имени колонки часто даёт `None`. Для надёжности сопоставляй колонки **по цифрам/буквенно-цифровому суффиксу**, а не по полному id.

  ```python
  import re
  pid_digits = re.findall(r'\d+', pid)
  for col in columns[1:]:
      if re.findall(r'\d+', col) == pid_digits:
          target_col = col
          break
  ```

- **features и template_data.bullets — разные слои.** Карточка товара (`ProductCard.tsx`) показывает `product.features`; описание под ней — `template_data.bullets`. Если убрать дубли только в одном месте, пользователь всё равно увидит дубль на странице. Чистить оба.
- **Пустые `features` после очистки — нормально.** Если все короткие галочки были чистыми характеристиками, карточка останется без списка «Особенности». Это ожидаемый результат выбора «не дублировать характеристики».

## Проверка после миграции

1. `npm run build` — должен пройти без ошибок.
2. Открыть товары с новыми spec-таблицами (`unisil-9638`, `luminofor`) и убедиться, что таблица отображается.
3. Открыть товары из семейных таблиц (`unisil-9331`, `unisil-9512`) и убедиться, что характеристики не дублируются в тексте.
4. Проверить, что короткие `features` (галочки в карточке) остались на месте.
5. **После любого изменения DB-записей перезапустить dev-сервер**, потому что Next.js/Turbopack кэширует SSG-страницы в памяти и может показывать старую версию.

## Что именно дублировалось в этом проекте

В `pentajunior-v2` технические характеристики продукта жили сразу в нескольких местах:

- `products.features` — короткие галочки в карточке товара (`ProductCard.tsx` рендерит именно их).
- `products.template_data.bullets` — список под описанием, который рендерит универсальный шаблон.
- `products.template_data.body` / `intro` — текст описания, часто содержащий те же цифры.
- `spec_tables` — семейные сравнительные таблицы или персональные таблицы для товаров без семейной.

Поэтому «удалить дубли» пришлось для **каждого** из этих слоёв, а не только для `template_data`. Проверяй все источники, иначе дубли останутся на странице.
