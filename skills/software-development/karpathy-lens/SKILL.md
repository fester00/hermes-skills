# Karpathy Lens

Практический lens для написания, ревью и рефакторинга кода. Помогает избежать типичных LLM-ошибок: скрытых предположений, раздутых абстракций, побочных правок и целей без проверки.

**Компромисс:** смещение к осторожности вместо скорости. Для тривиальных задач — используй здравый смысл.

## Когда применять

- Пользователь просит написать, изменить или починить код.
- Ревью недавних изменений — своих или чужих.
- Планируешь рефакторинг.
- Подготавливаешь план перед исполнением.

Не применяй как отдельный процесс для однострочных правок, очевидных фиксов и чистых вопросов без кода.

## Применение

Каждый раз, перед тем как писать или редактировать код, пройди четыре проверки. Ответы должны быть в мыслях или в кратком ответе пользователю — не оставляй скрытыми.

### 1. Think Before Coding — сначала мышление

**Не предполагай. Не скрывай непонимание. Показывай компромиссы.**

Что сделать перед кодом:
- Перечисли предположения явно. Если не уверен — спроси.
- Если запрос можно понять по-разному, назови варианты, не выбирай молча.
- Если есть более простое решение — скажи. Отстаивай его, когда это уместно.
- Если что-то непонятно — остановись, назови непонятное, задай вопрос.

**Анти-пример:** «Я сделал X, потому что подумал, что тебе нужно Y».  
**Пример:** «Есть два прочтения: (A) … (B) … Какое верно? Если B, то проще через Z».

### 2. Simplicity First — минимум кода

**Минимальный код, решающий задачу. Ничего спекулятивного.**

- Не добавляй фич вне запроса.
- Не создавай абстракции для одноразового кода.
- Не вводи «гибкость» или конфигурации без запроса.
- Не обрабатывай ошибки в невозможных сценариях.
- Если написал 200 строк, а можно 50 — перепиши.
- Проверка: «Сеньор-инженер сказал бы, что это переусложнено?» Если да — упрости.

**Анти-пример:** фабрика для одного продукта, интерфейс с одной реализацией, config-объект для значения, которое никогда не меняется.  
**Пример:** inline-решение или один helper, пока не появится второй use-case.

### 3. Surgical Changes — хирургические изменения

**Трогай только то, что нужно. Убирай только свой мусор.**

При редактировании существующего кода:
- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефакторь то, что не сломано.
- Соблюдай существующий стиль, даже если бы сделал иначе.
- Если видишь несвязанный мёртвый код — упомяни, но не удаляй.

Если твои изменения создают сирот:
- Удаляй импорты, переменные и функции, которые стали неиспользуемыми из-за твоих изменений.
- Не удаляй заранее существовавший мёртвый код, пока не попросят.

**Тест:** каждая изменённая строка прослеживается к запросу пользователя.  
**Анти-пример:** заодно переименовал переменные в соседней функции.  
**Пример:** diff содержит только строки, связанные с багом/фичей.

### 4. Goal-Driven Execution — цель и проверка

**Определи критерии успеха. Крути цикл, пока не проверишь.**

Превращай императивные задачи в проверяемые цели:
- «Добавь валидацию» → «Напиши тесты на невалидные входы и заставь их проходить».
- «Почини баг» → «Напиши тест, который его воспроизводит, и заставь его проходить».
- «Отрефакторь X» → «Убедись, что тесты проходят до и после».

Для многошаговых задач используй план с verify:
```
1. [Шаг] → verify: [команда/проверка]
2. [Шаг] → verify: [команда/проверка]
3. [Шаг] → verify: [команда/проверка]
```

**Анти-пример:** «Готово» без запуска проверки.  
**Пример:** каждый шаг завершается конкретной командой и её выводом.

## Интеграция с другими навыками

- С : применяй как lens на фазах Design, Execute, Verify. Не заменяет workflow — добавляет четыре проверки к каждому решению.
- С ``: `` даёт лестницу «как сделать меньше», `karpathy-lens` — правила «как не навредить». Используй вместе: сначала лестница , затем проверки karpathy-lens.
- С `code-quality-gates`: Goal-Driven Execution перекликается с Gate 1 (TDD) и Gate 3 (pre-commit verification). Используй `code-quality-gates` для конкретных команд и циклов.

## Как понять, что lens работает

- В diff меньше несвязанных изменений.
- Меньше переписываний из-за переусложнения.
- Уточняющие вопросы появляются до кода, а не после ошибок.
- PR/ветки чистые и минимальные.
