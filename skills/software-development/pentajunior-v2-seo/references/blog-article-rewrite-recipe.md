# Рецепт: рерайт существующей статьи блога pentajunior-v2

Принципиальное отличие от `blog-article-format-and-publishing-recipe.md` (создание с нуля): рерайт существующей статьи требует **DNA-паспорта** перед правкой, согласования scope (что нельзя трогать) и проверки результата через humanizer-скилл. Этот процесс применяли на сессии 2026-08-18 при работе со статьёй `kak-vybrat-silikon-dlya-form` (article-01).

## Когда применять

- Заказчик или редактор просит «освежить» / «сделать более человечным» / «убрать AI-слоп» статью блога.
- SEO-аудит показывает, что текст не отвечает требованиям Yandex к AI-контенту (нет полезных идей, шаблонные формулировки, нет явных ответов на интент).
- Нужно улучшить readability без потери индексации.

## Чего нельзя трогать по умолчанию (защитный каркас)

Эти поля не трогаем при рерайте, если пользователь явно не разрешит:

- `id`, `title`, `metaTitle`, `metaDescription`, `keywords`
- `category`, `relatedProducts`, `relatedCategories`
- `publishDate`, `readTime`, `published`

Причина: правка `metaTitle` / `metaDescription` / `keywords` воспринимается Яндексом как «новая страница» в части поисковых сигналов — теряем индексацию по старым ключам.

`content` — единственное поле, которое переписываем.

## Шаблон процесса (одна статья за раз)

Работаем по одной статье, чтобы не размазывать внимание. Пользователь применял именно такой паттерн: «да, по одной».

### Шаг 0. Загрузить навыки

Перед стартом **загрузить `humanizer`** (паттерн против AI-слопа) и **`yandex-seo-optimization`** (методология). Это не опционально — пользователь явно спросил «применяешь humanise?» в одной из сессий, ожидая, что эта проверка будет встроена в процесс.

### Шаг 1. Прочитать весь файл статьи целиком

Не кусками — `read_file` без offset/limit. Составить **DNA-паспорт**: что обязательно сохранить.

### Шаг 2. Согласовать с пользователем 3 вопроса

Все три вопроса задавать через `clarify` с вариантами, прежде чем менять текст:

1. **Meta:** трогаем `metaTitle` / `metaDescription` / `keywords` или нет? (по умолчанию — не трогаем).
2. **Голос:** «эксперт от первого лица» / «нейтрально-редакционный» / «мастер-практик»? (по умолчанию — нейтрально-редакционный).
3. **Глубина:** лёгкая чистка / средний рерайт 70–80% / глубокий рерайт с пересборкой? (по умолчанию — средний).

### Шаг 3. Зафиксировать ограничения по контенту

В проекте действуют конвенции:

- **Пищевая / медицинская отрасль / FDA / BfR / «кондитерские»** — для большинства линеек упоминания **убираются полностью из тела** (не смягчаются). В таблице сравнения строка «Пищевой контакт» удаляется целиком. Исключения с подтверждённым сертификатом: **ТСМ-1** (расширенная пищевая тематика легитимна: хлебопечение, кондитерка, упаковка, заморозка полуфабрикатов, промышленная сушка) и **Si-M в пищевом исполнении** (формы, лотки, противни — с явной отсылкой к сертификату партии). Когда в той же статье упоминаются и сертифицированные, и несертифицированные продукты, применяем правило только к несертифицированным.
- **«Производитель» / «от производителя»** — убирать, если компания дистрибьютор. Заменять на «купить», «в наличии», «официальный дистрибьютор».
- **Цена в тексте** — запрещена (только в карточке товара).
- **Обороты «дышит» / «кожа дышит» / «разведение» / «разводится»** — заменять или удалять.

### Шаг 4. Маркеры `{product:ID}` и `{category:slug}`

Эти плейсхолдеры — **часть SEO-каркаса** (внутренние ссылки на каталог). Их нельзя:

- удалять,
- переносить в другое место без причины,
- переименовывать (ID должны совпадать с `products.id` и `categories.slug` в SQLite).

### Шаг 5. Сбор данных по ключевым словам (SEO-проход)

Перед перепиской вступления имеет смысл собрать реальные SERP-данные:

1. Запросы из `keywords` текущей статьи + 2–3 смежных.
2. Запрос к Яндексу через `playwright-web-search` (Xvfb + persistent profile) — ищем топ-5 URL конкурентов.
3. Парсим первые 3–5 абзацев и `<h2>` топ-конкурента — чтобы понять «интент», обещания вступления, LSI-якоря.
4. Составляем список LSI-маркеров, которые нужно встроить в наше вступление.

Если нет возможности собрать данные (нет времени на Playwright), всё равно проходим требования Yandex к GEO/AI-поиску:
- Прямой ответ «что такое X» в первом абзаце.
- Перечисление факторов «чтобы выбрать X, определите 1, 2, 3, 4».
- LSI-маркеры из выдачи в первом экране.

### Шаг 6. Переписать `content` (70–80% текста)

Стоп-фразы и антипаттерны `humanizer`-скилла, которые часто встречаются в AI-генерации:

- Псевдо-статистика («на 80% определяется», «в 95% случаев» — если цифра не подтверждена).
- Анонсы содержания («Ниже — все ключевые параметры», «В этом материале —»).
- CTA-пересказ («Разобравшись в марках, проще получить нужный результат»).
- Продуктовые вставки во вступлении (сначала ответ на интент, потом ссылка на каталог).
- Пассивный залог с опущенным субъектом.

### Шаг 7. Build gate

Обязателен. В проекте используется npm wrapper через pnpm, но в среде может быть только `node_modules/.bin/`. Использовать:

```bash
export PATH="/home/natan/.nvm/versions/node/v24.13.1/bin:$PATH"
cd /home/natan/pentajunior-v2
./node_modules/.bin/tsc --noEmit
rm -rf .next tsconfig.tsbuildinfo
./node_modules/.bin/next build
```

Ожидаемый результат: `Compiled successfully` + `Generating static pages (158/158)`. Если в среде только `node` 18.x — Next.js 16 потребует Node ≥20.9; переключаем через nvm. До рерайта `article-05` под новую тему (ремонт силиконовой формы) ожидаемое число было 157/157; после — 158/158, потому что новая `article-05` теперь `published: true`. Фиксировать ожидаемое число перед каждым build gate, чтобы сразу заметить аномалию (например, 159/159 укажет на лишнюю опубликованную страницу).

### Шаг 8. Показать diff и ждать «давай»

По конвенции проекта — не коммитим без явного разрешения. Показываем:

- список изменённых фрагментов (было → стало),
- для больших правок — git diff по файлу.

### Шаг 9. Коммит и переход к следующей

Только по команде «давай». В коммит-сообщении — название статьи (article-ID + тема).

## Pitfalls

1. **Не загрузить `humanizer` заранее.** Пользователь явно указал, что ожидает применение humanizer-прохода. Просто «написать нейтрально» — недостаточно. Нужно пройти по 34 паттернам из humanizer-скилла.
2. **Смягчить вместо удалить.** «Пищевая промышленность» для несертифицированных линеек — это не смягчаемый признак, это удаляемый. Не предлагать «медицинские и пищевые применения (при наличии сертификации)» для Юнисил/Пентэласт — пользователь сказал «убираем из текста применения к пищевой и медицинских отраслях». ТСМ-1 и Si-M food-grade — исключения, см. выше.
3. **Подменить «Пищевой контакт» в таблице на нейтральную характеристику.** По решению пользователя — строка удаляется целиком, не заменяется. Для ТСМ-1 и Si-M food-grade статья целиком может быть пищевой — там правило не применяется.
4. **Менять `keywords`.** При среднем рерайте не трогаем `keywords`. Если очень хочется — отдельное согласование.
5. **Запускать `npm run build` без nvm.** В проектной среде может быть только Node 18.x; Next.js 16 требует ≥20.9. Всегда используем nvm-версию.
6. **Запускать `dev`/`start` после правок.** Не нужно — пользователь сам проверит локально. Достаточно typecheck + build.
7. **«Закоммитить самому».** Без «давай» — только показать diff.
8. **`relatedProducts` как comma-separated string вместо массива.** Реальный баг в `article-16` до рерайта: `relatedProducts: ["penta-811,penta-870"]` — TypeScript принял, но это один элемент массива `"penta-811,penta-870"`, а не два `["penta-811", "penta-870"]`. Перед каждым рерайтом grep'ом проверять `relatedProducts` на запятые внутри кавычек — если есть, разбить на массив. Паттерн поиска: `grep -E 'relatedProducts:\s*\["[^"]*,[^"]*"\]' src/data/blog/`.
9. **Путать «пищевая тематика допустима» с «всегда пиши про еду».** Правило работает только для конкретных продуктов с сертификатом. Не расширять пищевую тематику на линейки без сертификата только потому, что «пользователь разрешил про ТСМ-1».

## Чек-лист перед коммитом

- [ ] `metaTitle`, `metaDescription`, `keywords`, `id`, `relatedProducts`, `relatedCategories` — НЕ изменены.
- [ ] `relatedProducts` — массив правильной формы (нет запятых внутри кавычек): `grep -E 'relatedProducts:\s*\["[^"]*,[^"]*"\]' src/data/blog/`.
- [ ] Все маркеры `{product:ID}` и `{category:slug}` — на месте.
- [ ] Цифры и единицы — сохранены (Шор, вязкость, мПа·с, температура, и т.п.).
- [ ] Таблицы — тело ячеек не изменено (кроме случаев удаления строки Пищевой контакт).
- [ ] Нет «от производителя», «производитель» в обновлённом тексте.
- [ ] Нет «пищевая / медицинская / FDA / BfR / кондитерская» в обновлённом тексте (для линеек без сертификата).
- [ ] Нет псевдо-статистики и анонсов содержания.
- [ ] `npx tsc --noEmit` — без ошибок.
- [ ] `next build` — Compiled successfully + 158/158.
- [ ] Git diff показан пользователю.
- [ ] Получено «давай» перед `git commit`.
