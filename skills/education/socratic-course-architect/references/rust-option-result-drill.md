# 🦀 Практика: Option, Result и Pattern Matching

## Формат подачи

- Одна задача за раз. Ждём решение ученика. Разбираем. Только потом следующая.
- Градиент: простые (1–4) → средние (5–7) → сложные (8–10).

---

## Задача 1: «Удвоение в коробке» (Option + match)

```rust
let num = Some(7);
// match: если Some → умножить на 2, если None → -1
```

**Типичная ошибка ученика:** нет. Простая задача для разминки.

---

## Задача 2: «Если есть — приветствуем» (if let)

```rust
let maybe_name: Option<&str> = Some("По");
// if let Some(name) → "Имя: {name}", иначе → "Безымянный"
```

**Типичная ошибка:** нет.

## Задача 3: «Деление безопасное» (Result + match)

```rust
fn safe_divide(a: f64, b: f64) -> Result<f64, &'static str>
// match: Ok → "Ответ: {value}", Err → "Ошибка: {msg}"
```

**Типичная ошибка:** нет.

## Задача 4: «Скидка по умолчанию» (unwrap_or)

```rust
fn discount_percent(level: &str) -> Option<u8> { ... }
// discount_percent("gold").unwrap_or(0) → 20
// discount_percent("bronze").unwrap_or(0) → 0
```

**Типичная ошибка:** Путают переменные со строковыми литералами. Например, пишут `discount_percent("levelSilver")` (в кавычках, всё слитно) вместо `discount_percent(levelSilver)`.

**Урок:** В Rust строковый литерал и имя переменной — разные вещи. Компилятор не ругается, если тип совпадает (`&str`), но логика ломается.

---

## Задача 5: «Длина имени» (Option + map)

```rust
let maybe_name: Option<&str> = Some("Шифу");
// .map(|name| name.len()).unwrap_or(0)
```

**Типичная ошибка:** Ученик пишет `|s: &str| s.len()` — избыточная аннотация типа. Rust вывел бы сам.

**Урок:** В замыканиях Rust часто выводит типы. Явность допустима, но не обязательна.

---

## Задача 6: «Удвоение результата» (Result + map)

```rust
fn fetch_number() -> Result<i32, &'static str> { Ok(7) }
// result.map(|n| n * 2)
// match: Ok(v) → "Получено: {v}", Err(e) → "Ошибка: {e}"
```

**Проверка с Err:** Ученик изменил функцию на `Err("сетевой сбой")` и увидел, что `map` пропускает ошибку.

**Урок:** `Result::map` трансформирует только `Ok`. `Err` проходит сквозь.

---

## Задача 7: «Проверка возраста» (Option + and_then)

```rust
let input: Option<&str> = Some("42");
// .and_then(|s| s.parse::<i32>().ok())
// .and_then(|n| if n > 0 { Some(n) } else { None })
// .unwrap_or(0)
```

**Типичная ошибка:** Ученик использовал `for item in [input1, input2, input3, input4]` — массив `Option<&str>`, итерация по всем кейсам сразу.

**Урок:** Это корректный Rust, но подход «всё в одном блоке» отличается от пошаговой инкрементальной подачи. Важно показать, что `and_then` не создаёт `Option<Option<T>>`, а «разворачивает» в одну коробку.

---

## Задача 8: «Конфигурация с валидацией» (Result + map_err + and_then)

```rust
fn read_config(path: &str) -> Result<String, &'static str> { ... }

read_config(path)
    .map_err(|e| format!("Ошибка чтения: {}", e))
    .and_then(|content| content.parse::<u16>().map_err(|_| "не число".to_string()))
    .and_then(|port| if port > 1024 { Ok(port) } else { Err("порт зарезервирован".to_string()) })
```

**Типичная ошибка:** Опечатка `conten` вместо `content` в имени параметра замыкания.

**Урок:** Имена параметров замыканий — произвольны, но читаемость страдает.

---

## Задача 9: «Рефакторинг через ?» (Result + ?-оператор)

```rust
fn validate_port(content: &str) -> Result<u16, String> { ... }
fn load_and_validate(path: &str) -> Result<u16, String> { ... }
```

**Типичная ошибка УЧЕНИКА (важная):**
Ученик написал `?` внутри `for`-цикла в `main()`:

```rust
fn main() -> Result<(), String> {
    for item in ["config.txt", "missing.txt", "config.txt"] {
        let port = load_and_validate(item)?;
        println!("Порт: {}", port);
    }
    Ok(())
}
```

**Проблема:** `?` выходит из **текущей функции** при `Err`. При `item = "missing.txt"` программа аварийно завершается. Третья итерация не выполняется.

**Правильный путь для цикла:** Использовать `match` внутри цикла:

```rust
for item in [...] {
    match load_and_validate(item) {
        Ok(port) => println!("Порт: {}", port),
        Err(e) => println!("Ошибка для '{}': {}", item, e),
    }
}
```

**Урок:** `?` — для «провались вверх», когда одна ошибка = конец всего. `match` в цикле — для обработки каждого элемента отдельно. В бэкенде `?` удобен в рабочих функциях, но `main` требует осторожности.

## Задача 10: «Последний фильтр» (Синтез)

Написать `process_config(path: &str) -> Option<u16>` без `match`, только `?` и `.ok()`.

**Ожидаемое решение:**

```rust
fn process_config(path: &str) -> Option<u16> {
    read_config(path).ok()?
        .parse::<u16>().ok()?
        .and_then(|p| if p > 1024 { Some(p) } else { None })
}
```

**Альтернативное решение ученика (тоже принято):**

```rust
fn process_config(path: &str) -> Option<u16> {
    match read_config(path).ok()?.parse::<u16>().ok()? {
        p if p > 1024 => Some(p),
        _ => None,
    }
}
```

**Разбор:** `match` с охраной (`p if p > 1024`) — корректно, но не соответствует строгому заданию «только `?` и `.ok()`». В реальном коде оба встречаются.

## 📌 Выводы для будущих сессий

1. **Инкрементальная подача** (одна задача за раз) — оптимальна для закрепления синтаксиса. Ученик чувствует мгновенную обратную связь.
2. **Градиент сложности:** простые (match/if let) → средние (map/and_then) → сложные (map_err/?).
3. **Типичные ловушки Python/JS разработчиков в Rust:**
   - Путают переменные со строковыми литералами.
   - Думают, что `?` в цикле = «пропусти итерацию», а не «выйди из функции».
   - Избыточная аннотация типов в замыканиях.
   - Опечатки в именах параметров замыканий (не ловятся компилятором, но портят читаемость).
   - Использование `match` там, где задание требует цепочку комбинаторов — приемлемо, но стоит показать оба пути.
4. **Время жизни задач:** простые — 1–2 минуты, средние — 3–5, сложные — 5–10. Серия из 10 задач — это ~40–60 минут плотной практики.
